## When it fires

A `pub fn` inside an `#[contractimpl]` impl performs a storage mutation (`set`, `remove`, `update`) or a token operation (`transfer`, `transfer_from`, `mint`, `burn`), and no `require_auth` / `require_auth_for_args` call is reachable within one level of same-file helper calls.

Read-only functions are not flagged. `extend_ttl` is not privileged, so calling it alone does not count as a mutation that needs auth. A function whose receiver is an `Address` loaded from storage (`admin.require_auth()`) is the correct pattern, not a finding.

## Examples

Flagged — public function, no auth:

```rust
#[contractimpl]
impl Token {
    // error: SL001, no authorization check before a storage write
    pub fn set_admin(env: Env, new_admin: Address) {
        env.storage().instance().set(&AdminKey, &new_admin);
    }
}
```

Not flagged — auth present, including the storage-loaded `Address` form:

```rust
#[contractimpl]
impl Token {
    pub fn set_admin(env: Env, admin: Address, new_admin: Address) {
        admin.require_auth();
        env.storage().instance().set(&AdminKey, &new_admin);
    }
}
```

Not flagged — auth inside a same-file helper, one level deep:

```rust
fn authed_write(env: &Env, who: &Address) {
    who.require_auth();
}
```

## False positives and false negatives

**False positives.** A deliberately permissionless mutation can match the rule. On the benchmark corpus, four toy counter increments were arguable for this reason.

**False negatives.** Auth hidden in a macro, more than one helper call away, or in another file is not followed. The rule only follows same-file helpers one level deep.

## Suppressing this rule

Only after you have decided the function is intentionally permissionless, for example a deliberately public counter. Then name the rule on the function line:

```rust
// soroban-lint-ignore: SL001
pub fn increment(env: Env) -> u32 { /* ... */ }
```

A suppression with an unknown id produces an `SL000` warning, so a typo like `SL01` is caught rather than silently ignored.

## On the benchmark corpus

10 findings on the pinned corpus, none confirmed false positives. Four are arguable: `increment`-style functions on toy counters that match the rule's definition but are demonstrative examples where a shared counter may be intentionally permissionless. Three are true positives (`merkle_distribution::claim`, `pause::set`, `ttl::setup`).

SL001 originally reported 24 findings because it flagged `__constructor`, which runs once at deployment and needs no authorization. That was fixed in code, not documented away.
