## When it fires

A contract function contains `panic!`, `.unwrap()`, `.expect(..)`, `unreachable!`, `todo!`, `unimplemented!`, or an index/slice expression. In Soroban an unhandled panic aborts the whole invocation, so a panic in one branch takes down the transaction rather than returning an error.

`panic_with_error!` is **not** flagged — it is the recommended pattern. Neither are `?` propagation, `.unwrap_or`, `.unwrap_or_default`, or `.unwrap_or_else`.

## Examples

Flagged:

```rust
#[contractimpl]
impl Vault {
    // warning: SL002, panics instead of returning a typed error
    pub fn withdraw(env: Env, who: Address, amount: i128) {
        let bal = env.storage().persistent().get(&Balance(who.clone())).unwrap();
        // ...
    }
}
```

Not flagged — the recommended shape:

```rust
pub fn withdraw(env: Env, who: Address, amount: i128) -> Result<(), Error> {
    let key = Balance(who);
    let bal = env.storage().persistent().get(&key).ok_or(Error::NotFound)?;
    // ...
    Ok(())
}
```

The confidence difference matters. Explicit panics are `high` confidence; index expressions are `medium`, because the surrounding code may prove the index in bounds.

## False positives and false negatives

**False positives.** An index can be proven in bounds by surrounding logic the syntactic rule does not understand.

**False negatives.** A panic hidden inside a macro body or a helper outside the analyzed contract function can be missed.

## Suppressing this rule

Prefer `panic_with_error!` or a `Result` return over suppressing this rule — the fix is usually a few lines. Suppress when the invariant is enforced by the host or by a caller, and record why next to the directive:

```rust
// soroban-lint-ignore: SL002 -- index is checked in `resolve` above
let v = data[idx];
```

## On the benchmark corpus

62 findings, the largest single contributor on the pinned corpus. None confirmed false positives; 18 are arguable. Two land in `*test.rs` files, which is a known limitation rather than a rule defect — see below.
