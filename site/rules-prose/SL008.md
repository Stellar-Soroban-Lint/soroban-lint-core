## When it fires

Two independent checks, at different confidences:

- **`unsafe` (high confidence).** Any `unsafe` block, `unsafe fn`, `unsafe impl`, or `unsafe trait` in a contract crate. Contracts run in a constrained WASM sandbox and `unsafe` bypasses the guarantees that make them auditable.
- **Missing `#![no_std]` (low confidence).** A file carrying a `#[contract]` attribute that lacks `#![no_std]` at the crate root. A missing attribute links a std runtime the host does not provide.

`unsafe` inside `#[cfg(test)]` is not flagged. The `no_std` check applies only to `lib.rs` and `main.rs`, because `#![no_std]` is a crate-root attribute.

## Examples

Flagged:

```rust
// warning: SL008, unsafe block in a contract crate
pub fn read_raw(e: &Env) -> u32 {
    unsafe { *(e as *const Env as *const u32) }
}
```

The fix is to remove the `unsafe`, not to suppress the rule.

A valid pattern this rule reports as missing `no_std`:

```rust
#![cfg_attr(not(test), no_std)]
```

That is a documented false positive at low confidence, not a real finding.

## False positives and false negatives

**False positives.** A `cfg_attr` that supplies `no_std` can be reported because the rule looks for a literal crate-level `#![no_std]` attribute.

**False negatives.** `unsafe` or `no_std` context hidden in macros, or distributed across unsupported crate-root arrangements, is outside these syntactic checks.

## Suppressing this rule

For the `cfg_attr` form, the suppression belongs on the crate root line:

```rust
// soroban-lint-ignore: SL008 -- no_std is applied via cfg_attr below
#![cfg_attr(not(test), no_std)]
```

Suppressing the `unsafe` check is a different decision: it means asserting that the block is sound, which is an audit-grade claim, not a documentation one.

## On the benchmark corpus

0 findings on the pinned corpus, after a fix. It originally reported 4 because the `no_std` check applied to any file rather than the crate root, firing on `*/src/test.rs` and similar. That was fixed in code.
