## When it fires

A contract function writes `persistent` or `instance` storage with `set`, `remove`, or `update`, and the function contains no `extend_ttl` call. Those entries expire, so a write that never extends the TTL lets live state lapse and be archived.

`temporary()` writes are not flagged — expiring is what temporary storage is for. Read-only functions, functions that already call `extend_ttl`, and `__constructor` are also not flagged.

## Examples

Flagged — a persistent write with no TTL extension in the same function:

```rust
#[contractimpl]
impl Registry {
    // info: SL005, persistent write with no extend_ttl
    pub fn register(env: Env, name: Symbol) {
        env.storage().persistent().set(&name, &1u32);
    }
}
```

Not flagged:

```rust
pub fn register(env: Env, name: Symbol) {
    let key = name;
    env.storage().persistent().set(&key, &1u32);
    env.storage().persistent().extend_ttl(&key, THRESHOLD, EXTEND_TO);
}
```

## False positives and false negatives

**False positives.** A contract that extends TTL in a helper or a separate entrypoint can be reported because the rule checks the current function.

**False negatives.** TTL behavior hidden in a macro or helper is not followed; the rule only recognizes visible calls in that function.

## Suppressing this rule

This is `info` severity and experimental, and a common case is a contract whose entrypoint extends TTL centrally. Suppress per line when the extension lives in a helper or another entrypoint:

```rust
// soroban-lint-ignore: SL005 -- TTL is extended by `bump_all`
env.storage().persistent().set(&key, &value);
```

## On the benchmark corpus

21 findings on the pinned corpus, all arguable, none confirmed false positives. Each write is genuinely persistent or instance and genuinely lacks a same-function `extend_ttl`; the argument is that some contracts extend TTL elsewhere or rely on the default. Two land in `*test.rs` files.

Promotion to `stable` is deferred pending a larger corpus.
